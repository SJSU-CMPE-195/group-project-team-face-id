## Code changes (commit `5bf1728`)

### 1. Phantom face scans when the HC-SR04 is unplugged

**Problem:** With no sensor connected and nobody present, the event log showed
`START_AUTH UNLOCK` → 20 s scan timeout → new scan ~10 s later, forever.

**Cause:** GPIO33 (ECHO) was a plain `INPUT`. When unplugged it floats, and
`pulseIn()` read electrical noise as very short echoes (~1–2 cm). Three such
readings marked a person as present, and because noise never produces three
"far" readings, the person never "left". After each failed scan the sensor
re-armed after `REARM_MS` (10 s) and scanned again.

**Fix** (`ESP32_Program/ESP32_Program.ino`):

- `pinMode(ECHO_PIN, INPUT_PULLDOWN)` — an unplugged ECHO line reads LOW (no echo).
- New `MIN_ECHO_US = 116` (~2 cm, the HC-SR04 minimum range); shorter pulses
  are treated as no echo.
- `readDistanceCm()` returns "no echo" if ECHO is already HIGH before the
  trigger (a working sensor idles LOW).

Invalid readings count toward "gone", so no presence is detected. A connected
sensor behaves as before (the divider's 2 kΩ to GND still sets the level).

Also changed: `ESP32_Program/ReadMe.md` (presence table, "No valid echo" row)
and `tests/esp32/include/Arduino.h` (added the `INPUT_PULLDOWN` constant to the
firmware test stub so the existing harness compiles).

### 2. Auto-relock stopped the engine ~4 s after it started

**Problem:** Event log from a successful walk-up:

```
20:06:56  unlock   ok  (Granted: Adam)
20:07:02  ignition ok  start (auto ignition scan)
20:07:06  lock     ok  auto_relock_10s   <- engine stopped
```

The 10 s auto-relock timer armed at unlock was never cancelled when ignition
started. Relocking sends `STOP` + `LOCK`, so the engine only ran ~4 s.

**Fix** (`car_face_auth/src/runtime_actuation.py`):

- `_arm_auto_relock()` remembers the delay and user (`_relock_seconds`,
  `_relock_user_id`).
- `set_ignition()` — successful `START` cancels the pending relock timer.
- `set_ignition()` — successful `STOP` (manual, or the
  `ignition_timeout_<n>s` auto-stop) calls new `_restart_auto_relock()`, which
  re-arms the full countdown if the car is still unlocked. A failure to
  restart is logged as a `lock` / `fail` event.
- `_mark_locked()` clears the remembered values whenever the car locks.

An unlock **without** ignition still relocks after the configured delay, as before.

### 3. Phone did not show lock/ignition changes

**Problem:** The Console "Current state" card looked stuck on "Locked".

**Cause:** `pollConnected` waited 3 s *after* a full 6-request snapshot over
BLE (`/api/me`, `/api/status`, face-status, users, devices, logs), so each
refresh took ~5–8 s, and `/api/status` was read second so it was already old
when shown. Combined with issue 2 (≈6 s unlocked, ≈4 s ignition on), the phone
missed the changes entirely.

**Fix:**

- `AppViewModel.kt` `pollConnected`: every `STATUS_POLL_MILLIS` (1.5 s) load
  `/api/status` only (`loadDeviceStatus`); when not busy and
  `SNAPSHOT_POLL_MILLIS` (10 s) have passed, load the full snapshot instead.
  Existing 429 / error handling is unchanged.
- `AppStateTransitions.kt` `readSnapshot`: `/api/status` is now fetched
  **last**, so the other requests don't age the controller report.

## Expected behavior after a walk-up

| Time | ESP32 / host | Phone Console |
|---|---|---|
| 0 s | Face authorized → `UNLOCK` | Unlocking → Unlocked |
| ~5 s after lock stops moving | `START_AUTH IGNITION` (sent even if the person left) | Unlocked |
| ignition authorized | `START`, relock paused | **Ignition on** (green) |
| +20 s | `ignition_timeout_20s` → `STOP`, relock countdown restarts | Ignition off |
| +10 s more | `auto_relock_10s` → `STOP` + `LOCK` | Locking → Locked |

Timers come from Settings: Auto re-lock = 10 s, Ignition auto-stop = 20 s.

## What the states mean

The ESP32 reports its **commanded** controller state. The prototype has no lock
position sensor or motor rotation sensor, so none of these values prove the
physical position.

**Lock state** (ESP32 `STATE 1 <LOCK> <IGNITION>`, Pi `controller_state.lock`)

| ESP32 | Pi / API | Meaning |
|---|---|---|
| `LOCKED` | `locked` | Stepper finished moving to the locked position (or restored as locked at boot) |
| `UNLOCKED` | `unlocked` | Stepper finished moving to the unlocked position |
| `LOCKING` | `locking` | Lock command accepted; stepper is moving toward locked (~3–4 s) |
| `UNLOCKING` | `unlocking` | Unlock command accepted; stepper is moving toward unlocked |
| — | `unknown` | No valid report: ESP32 disconnected, older firmware, or last report ≥ 9 s old |

**Ignition state** (`controller_state.ignition`)

| ESP32 | Pi / API | Meaning |
|---|---|---|
| `ON` | `on` | Engine motor output enabled |
| `OFF` | `off` | Engine motor output disabled |
| — | `unknown` | Same conditions as lock `unknown` |

**When the ESP32 sends a `STATE` line:** at boot; when lock movement starts and
when it finishes; when the ignition output changes (not on a repeated
`start`/`stop` that changes nothing); and in reply to `STATUS`. A no-op
command (`lock` while already locked) prints `Already locked` and sends no
`STATE` line.

## API behavior

**Serial protocol (Pi ↔ ESP32, 115200 baud)** — additions on this branch:

| Direction | Message | Meaning |
|---|---|---|
| Pi → ESP32 | `STATUS` | Ask for the current controller state |
| ESP32 → Pi | `STATE 1 <LOCK> <IGNITION>` | Version-1 state report (values above) |

The Pi sends `STATUS` every 3 s on the existing serial writer. Authentication
messages (`START_AUTH`, `AUTHORIZED`, `AUTH_ACK`, …) are unchanged. Reports
are tied to the current serial connection and discarded when it closes.

**`GET /api/status`** (authenticated) — adds `runtime.controller_state` on the Pi:

```json
{
  "lockState": "locked",
  "ignitionOn": false,
  "runtime": {
    "controller_state": {
      "lock": "unlocking",
      "ignition": "off",
      "moving": true,
      "fresh": true,
      "age_ms": 120
    },
    "physical_state_confirmed": false,
    "actuator_feedback": "unavailable"
  }
}
```

| Field | Values | Meaning |
|---|---|---|
| `lock` | `locked` / `unlocked` / `locking` / `unlocking` / `unknown` | Controller lock state |
| `ignition` | `on` / `off` / `unknown` | Controller ignition output |
| `moving` | `true` (locking/unlocking), `false` (locked/unlocked), `null` (unknown) | Stepper in motion |
| `fresh` | `true` / `false` | `false` once the last report is ≥ 9 s old or the ESP32 disconnected |
| `age_ms` | integer or `null` | Time since the Pi received the report; `null` before the first report and after a disconnect |

- Top-level `lockState` and `ignitionOn` are unchanged. They are the **host's
  command state** (what the Pi last told the car), kept for older clients.
- `physical_state_confirmed` stays `false` and `actuator_feedback` stays
  `unavailable` on the Pi.
- PC simulation has no ESP32 controller report; clients show the simulated
  top-level `lockState`/`ignitionOn` instead.
- API protocol version remains **4**.

**`GET /local/pairing-qr`** (unchanged endpoint, now used by the dashboard) —
local-only, administrator session required. Returns `name`, `device_id` and a
PNG `qr_image`. A request from another machine gets 403. Shown by
**Settings → Device pairing QR** for admins only.

## What the phone UI shows

Console tab → **Current state** card (Pi host, real controller):

| `controller_state` (fresh) | Big label | Ignition chip | Chip color |
|---|---|---|---|
| `locked` | Locked | — | — |
| `unlocked` | Unlocked | — | — |
| `locking` | Locking | — | — |
| `unlocking` | Unlocking | — | — |
| ignition `on` | — | Ignition on | Green |
| ignition `off` | — | Ignition off | Grey |
| any value `unknown`, or not fresh | Unknown | Ignition unknown | Amber |

Caption under the card:

- Fresh report: *"Controller-reported state. Physical position is not confirmed."*
- Missing, invalid or stale: *"Controller status is unavailable or stale. Physical position is not confirmed."*

How the phone decides "fresh": it takes the Pi's `age_ms` and adds the time
elapsed on the phone since it sent the request. At 9 s total the card switches
to Unknown on its own, even if no new response arrives, so a dropped Bluetooth
link can't leave an old "Unlocked" on screen. If the JSON is malformed or
inconsistent (e.g. `moving` doesn't match `lock`), the card shows Unknown.

Refresh cadence: `/api/status` every ~1.5 s, full snapshot (users, faces,
devices, logs) every ~10 s. Status keeps refreshing while an enrollment is busy.

PC simulation host: shows the simulated Locked/Unlocked and Ignition on/off from
top-level `lockState`/`ignitionOn`, with no caption.

Dashboard (web, Pi): **Settings → Device pairing QR → Show pairing QR** shows
the host name, Device ID and QR; **Hide pairing QR** removes it; errors show a
message and **Retry**. The card is cleared on logout or account change.

## HC-SR04 wiring

The divider is required whether or not the LCD is connected — it protects
GPIO33 from the sensor's 5 V ECHO output.

| HC-SR04 | ESP32 |
|---|---|
| VCC | 5V / VIN |
| GND | GND |
| TRIG | GPIO32 (direct) |
| ECHO | 1 kΩ → GPIO33, and 2 kΩ from GPIO33 → GND |

Only a 3.3 V-capable module (HC-SR04P / RCWL-1601) powered from 3V3 can skip the divider.
